Layout: ProductExchMappingV3 (ID: 9130)

EXCHANGE-ASSIGNED IDENTIFIERS - one row per (instrument, venue). The ephemeral, hot half of what was one ProductMapping table. | THIS RECORD (exchange) | ProductMapping (registry/vendor) lifecycle | EPHEMERAL - intraday to weekly | PERMANENT identity residency | HOT, resident in every routing | reference data | and ingest process | writers | PER-EXCHANGE FEED HANDLERS | vendor loaders (EDI, GLEIF, OpenFIGI) volume | 10^4 - 10^5, churning daily | one ISIN per instrument The writer axis is the one that forces it rather than merely favours it - the same reason SpreadExchID exists as rows instead of a repeater. A table written by per-venue handlers and by vendor loaders together has two purge horizons and two hot/cold profiles in one resident set. THERE IS NO extKeyType HERE, AND THAT IS THE POINT. For an exchange-assigned identifier the TYPE AND THE AUTHORITY ARE THE SAME FACT - 'CBOE's id for this thing' - so the venue IS the type. mic is key material and no separate type field is needed. That collapses the old venue-scoped-versus-global question rather than answering it.
